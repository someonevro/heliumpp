## 3. Browser vision and architecture

The intended foundation is ungoogled-chromium.

The final application must be a genuine desktop browser that navigates real websites, not a mockup, simulated browser, or standalone webpage with fake controls.

Before implementing the application, investigate:

- Forking and patching ungoogled-chromium directly.
- Using Chromium Embedded Framework (CEF).
- Using an existing browser codebase or another maintainable Chromium integration.
- The architecture used by Helium Browser, especially its Chromium modifications, extension support, and uBlock Origin integration.

Compare feasibility, maintenance costs, build requirements, licensing, security, DRM, extension support, and UI flexibility.

Do not silently substitute Electron, WebKit, or another browser engine. Explain any proposed alternative and its consequences before committing to it.

Initially target Linux desktop systems, particularly Arch-based systems such as Omarchy and Debian/Ubuntu-based distributions. Keep the design extensible to Windows and macOS.

Prefer open-source components and maintainable solutions. Document dependencies, licences, platform limitations, and upstream security maintenance requirements.

## 5. First-launch privacy selector

On the first launch, show a polished onboarding screen offering these five privacy presets and one additional ad-blocking-only mode.

The selected mode must persist across restarts and be changeable later through a simple setting. Show users what each mode actually enables.

### Low — Familiar Browsing

Target an approximate level of protection comparable to Firefox with uBlock Origin and sensible defaults.

Provide effective ad and tracker blocking, basic third-party tracking protection, reasonable cookie restrictions, and good website compatibility. Avoid unnecessarily aggressive fingerprinting countermeasures.

Do not claim exact equivalence to Firefox.

### Medium — Recommended

**This must be the highlighted default recommendation for ordinary users.**

Provide strong ad and tracker blocking, malicious-domain protection, sensible third-party cookie restrictions, practical fingerprinting mitigations, reasonable referrer and permission policies, and minimal unnecessary background activity.

Prioritize everyday usability, including video streaming, sign-in, banking, and web applications.

This mode should balance privacy, security, compatibility, and performance.

### High — Hardened Privacy

Aim for a LibreWolf-inspired privacy philosophy using Chromium's actual capabilities.

Provide more aggressive tracker blocking, stricter third-party cookie and storage restrictions, tighter referrer policies, restrictive permissions, available fingerprinting mitigations, and reduced unnecessary background activity.

Warn users that some websites may malfunction and offer understandable site-specific exceptions.

Do not claim feature parity with LibreWolf when Chromium lacks equivalent protections.

### Ultra — Maximum Practical Privacy

Provide the strongest practical privacy configuration without promising perfect anonymity.

Use strict tracker blocking, aggressive cookie and storage partitioning, restrictive permissions and referrer policies, available fingerprinting protections, and minimization of optional telemetry and background network requests.

Provide site-specific exceptions and clearly explain the trade-offs.

Never disable essential certificate validation, security protections, or security updates just to claim maximum privacy.

### Ad Blocking Only

Enable effective ad blocking and basic malicious-domain protection while keeping other privacy settings close to normal browser defaults.

Do not enable aggressive fingerprinting defenses or additional restrictions beyond baseline security unless the user explicitly chooses them.

Explain that this mode does not offer the same privacy protection as the other presets.

## 6. Real privacy enforcement

These presets must change actual browser behavior. They must not be cosmetic labels.

Build a centralized, declarative privacy configuration system with:

- Explicit settings for every preset.
- Persistent configuration and validation.
- A visible summary of active protections.
- A reset-to-preset option.
- Immediate application where technically possible.
- Restart notifications where necessary.
- Site-specific exceptions.
- Tests verifying that each preset produces the expected behavior.

Identify which settings can be controlled through existing Chromium APIs, which require browser-level modifications, and which are impossible or unreliable.

Document limitations instead of pretending unsupported controls work.

## 7. Built-in ad blocking — important

I want **uBlock Origin-level content blocking, similar to the integration in Helium Browser**, rather than a basic DNS blocker.

Investigate Helium's public source code and its uBlock Origin integration before choosing an implementation.

Evaluate:

- Bundling and maintaining full uBlock Origin with appropriate Chromium extension support.
- Supporting Manifest V2 where necessary, including the maintenance burden of Chromium patches.
- Using uBlock Origin Lite or a suitable native content-blocking engine if full uBlock Origin is impractical.
- Maintaining compatibility with modern Chromium releases.

Do not assume these alternatives provide equivalent functionality. Explain their differences before deciding.

The browser should provide:

- Strong ad, tracker, and malicious-domain blocking.
- Maintained filter lists with automatic updates.
- Local filter-list caching.
- Per-site blocking controls and allowlists.
- A blocked-request counter and visible protection status.
- Support in normal and supported private-browsing sessions.
- Reasonable CPU, memory, and startup performance.

Do not invent a replacement for uBlock Origin or copy its implementation without respecting its licence.

Investigate extension APIs against the actual Chromium version selected. Keep filter-list updates independent of browser releases where practical.

## 8. DRM and streaming

I want DRM-protected websites to work out of the box wherever legally and technically possible.

Investigate a legitimate Widevine Content Decryption Module integration and support for Encrypted Media Extensions.

Aim to support services such as Netflix, Spotify Web Player, and YouTube, subject to their current technical and licensing requirements.

Also investigate required codecs, audio support, hardware video decoding, and GPU acceleration.

Provide a diagnostic page showing DRM status, codec availability, and missing dependencies.

Do not pirate, reverse-engineer, bypass DRM, or redistribute proprietary components without permission.

If Widevine cannot legally be bundled, implement the most convenient legitimate setup path available. Document any required user action and never claim that DRM works until it has actually been tested.

## 14. Cross-Platform Strategy — Desktop and Mobile

The long-term goal is to deliver this browser on all five major target platforms:

- Linux
- Windows
- macOS
- Android
- iOS

Cross-platform support is a core product requirement, not an optional future enhancement. However, do not promise identical features or a shared rendering engine on every platform when technical or platform restrictions prevent it.

### Architecture requirements

Before committing to the initial architecture, research and document the feasibility of every target platform.

Investigate the official ungoogled-chromium platform repositories, Chromium's supported build targets, mobile browser requirements, extension support, DRM restrictions, and distribution requirements.

The desktop application should use ungoogled-chromium wherever practical.

For Android, investigate the official ungoogled-chromium Android project and determine how much of the desktop browser's privacy system, user interface, and configuration can be shared with a mobile implementation.

For iOS, investigate Apple's current browser-engine requirements, available alternative-engine entitlements, App Store rules, and regional restrictions. Do not assume that an ungoogled-chromium engine can be shipped on iOS globally. If a WebKit-based implementation is required, assess whether a separate iOS browser can preserve the product's privacy philosophy and user experience.

### Shared functionality

Design the architecture so that the following components can be shared wherever practical:

- Privacy preset definitions and configuration schema.
- Ad-blocking rules and filter-list management.
- Privacy and security policy definitions.
- Settings data model.
- Bookmarks, history, and user preferences where compatible.
- Onboarding text and privacy explanations.
- Design tokens, icons, and visual identity.
- Tests for platform-independent logic.
- Documentation and release procedures.

Do not force shared code where platform-specific implementations are safer or more maintainable.

### Platform-specific interfaces

Create interfaces appropriate to each platform.

Desktop:
- Zen-inspired vertical tabs and workspaces.
- Keyboard shortcuts, desktop window controls, downloads, and extensions where supported.

Android:
- Touch-friendly navigation and tab management.
- Mobile-appropriate settings and privacy controls.
- Battery, memory, and performance considerations.
- Appropriate Android lifecycle and background behavior.

iOS:
- Native-feeling navigation and touch controls.
- Platform-compliant browser engine and extension capabilities.
- iOS-specific storage, permissions, privacy, and lifecycle behavior.

Do not attempt to copy the desktop interface directly onto mobile screens.

### Feature compatibility matrix

Maintain a platform compatibility matrix covering:

- Browser engine and rendering.
- Privacy presets and enforcement.
- Ad and tracker blocking.
- Extension support.
- DRM and streaming.
- Codec and hardware acceleration support.
- Bookmarks, history, and downloads.
- Private browsing.
- Tab synchronization, if implemented.
- Security updates and distribution.

For every feature, identify whether it is supported, partially supported, unsupported, or not yet tested on each platform.

Do not advertise a feature on a platform until it has been implemented and verified there.

### Development order

Develop in stages:

1. Research all five platforms and identify architectural constraints.
2. Choose a maintainable architecture with explicit platform boundaries.
3. Build and validate a working desktop prototype.
4. Stabilize shared privacy, configuration, and content-blocking components.
5. Investigate and implement the Android version.
6. Investigate and implement the iOS version, including any required engine differences.
7. Establish automated testing, packaging, signing, distribution, and security updates for every supported platform.

Desktop development may be the first implementation milestone, but it must not create unnecessary architectural barriers to mobile development.

Document all platform limitations honestly and propose legitimate alternatives where exact feature parity is impossible.
